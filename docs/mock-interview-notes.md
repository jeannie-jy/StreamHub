## Q002：送礼链路中的订单与消息一致性

**面试官问题：** 一个用户点击送礼后，你为什么不在 HTTP 接口里同步扣款、给主播入账，而要引入 RocketMQ？假设你先把订单写入 MySQL，随后发送 MQ 消息时服务宕机了，这笔订单怎么办？请按项目实际实现说明。

**用户回答：** 如果直接在 HTTP接口里同步扣款给主播入账的话，这时如果网络断开的话，可能会造成重复扣款现象。然后如果把订单写进 MySQL，准备发消息时服务突然宕机，那么这时 Outbox消息它一直会标记成待发送的状态。然后在网络重连之后，Outbox消息会再次发送到 RocketMQ中，所以不用担心这次支付会重复处理，或者是不会完成。

**评价与改进：** 抓住了 Outbox 持久化后可补发的关键，但以下边界需要纠正：

1. 网络断开本身不会直接重复扣款；典型情况是服务端已提交、客户端未收到响应，客户端重试且服务端缺少幂等控制。同步和异步都要处理该问题，MQ 不是防重复扣款的充分条件。
2. 引入 MQ 的主要价值是异步处理、缓冲突发流量、控制消费速度和重试；同步本地事务也可以正确完成账务。当前建单仍需访问并写入 MySQL，不能声称 MQ 隔离了全部入口数据库压力。
3. 订单和 Outbox 必须在同一个本地事务内提交。若宕机发生在提交前，则两者回滚；提交后尚未发送，则持久化事件可由恢复后的后台投递器扫描补发。服务宕机需要服务恢复，仅客户端网络重连不足以触发后台恢复。
4. Outbox 不一定一直是 PENDING：投递认领后是 SENDING，超时可回收；发送成功标记 SENT，重试耗尽可能进入 FAILED。恢复与补偿有前提，不能承诺所有订单必定成功，余额不足也会使订单失败。
5. 发送成功但标记 SENT 前宕机会导致重发。Outbox 解决订单与待发送事件的原子落库及可恢复投递，账务幂等依靠消费者事务、订单行锁与状态检查、流水唯一约束。
6. 这里是虚拟金币送礼，不应扩展描述为已接入真实支付。

**参考答案（可口述）：**

同步扣款并非做不到。观众扣款、主播入账和流水可以放在同一个 MySQL 事务中完成；即使改成异步，也仍然需要处理客户端重试。因此，我引入 MQ 主要是为了把请求接收与账务处理解耦，缓冲突发请求并支持后台重试，代价是增加消息积压、异步延迟和运维复杂度。当前建单仍访问 MySQL，MQ 主要缓冲后续处理。

为避免订单写入成功而消息没有发出去，我在同一个本地事务中创建 PENDING 订单和 Outbox 事件。事务提交前宕机，两者一起回滚；提交后、发消息前宕机，事件仍在数据库中，服务恢复后由定时投递器扫描补发。对于卡在 SENDING 的事件，也有超时回收机制；重试耗尽进入 FAILED 后，需要通过补偿或运营重试处理，不能保证只要网络恢复就一定成功。

另一个窗口是 Broker 已接收消息，但服务还没把 Outbox 标成 SENT 就宕机，这会造成重复投递。因此消费者还要保证幂等：在同一事务中锁定订单，只有 PENDING 才执行账务，完成扣款、入账、唯一流水和订单状态更新；重复消费看到终态就跳过。Outbox 负责可恢复投递，消费者幂等负责避免重复账务生效。

**代码核对：** GiftService.placeOrder/processOrder、MqOutboxRepository 的 claim/markFailure/recoverStaleSending/retryFailed，以及 MqOutboxDispatcher 的调度入口。本轮未运行测试。

## Q003：并发重复消费下的账务幂等

**面试官问题：** 同一笔送礼订单的两条重复消息，被两个消费者同时处理。如果只是先查订单状态，发现 PENDING 就扣款，会出什么问题？你项目里具体用什么 SQL、把哪些操作放在同一个事务里，才能保证只扣一次？

**用户回答：** 在消费者收到宝贝消息之后，他首先会锁定订单，然后再检查当前的订单状态。所以说不会存在有两个消费者同时进行扣款和收款的操作。因为在消费者锁定订单之后，他会在同一个本地事务中执行整套资金和订单的变更。然后必须要把观众扣款、主播收款、订单状态变更这些操作都放在同一个事务里面。

**评价与改进：** 核心正确：先锁定订单再检查状态，资金与订单变更在同一事务中完成。需补充锁的实现为数据库 SELECT ... FOR UPDATE，锁保持到事务结束；第二个消费者等待后进行锁定读，看到前一个事务提交后的终态而跳过；流水写入也必须纳入同一事务，异常时整笔回滚。该锁串行化的是同一订单的处理，不能泛化为所有订单不能并行扣款，不同订单共享钱包的并发还需要钱包级保护。

**参考答案（可口述）：**

项目在 GiftService.processOrder 上开启本地事务，先通过 SELECT ... FOR UPDATE 锁定订单，再检查状态，只有 PENDING 才继续处理。两个消费者处理同一订单时，后一个会等待订单锁；前一个提交成功后，后一个拿到锁，通过锁定读看到订单已是 SUCCESS，就直接返回，不再执行账务。如果前一个事务失败并回滚，后一个可以继续处理仍为 PENDING 的订单。

扣款、主播入账、双方钱包流水和订单成功状态必须在同一个事务内提交或回滚。项目还会锁定双方钱包，在锁内检查余额并更新；流水使用基于订单号的唯一业务号作为额外约束。这里依靠的是数据库事务和锁，不能只做普通查询后在内存中判断。

关键 SQL 的简化表达为 SELECT * FROM gift_order WHERE order_no = ? FOR UPDATE；实际仓库查询还关联了礼物目录。事务方法由独立的 GiftOrderMessageListener 调用；processOrder 返回并完成事务提交后，监听器才继续发布成功事件和返回消费结果。本轮未运行测试。

## Q004：不同订单争用同一个钱包

**面试官问题：** 同一个观众余额只有 100，同时发起两笔不同订单，每笔送礼 80。两笔订单各自锁住自己的订单行，还能防止余额被重复使用吗？请说明不加钱包并发保护可能出现的结果，以及项目中如何保证只有一笔能扣款成功。

**用户回答：** 嗯，这个时候应该组就没有用了，所以它会发起扣款服务。但是，但是在实际的交易中，如果说他发现这个钱，就是在真实的扣款中，它总会有一个消费者扣款余额不足，所以就可以保证只有一笔扣款成功。

**评价与改进：** 意识到只锁不同订单无法保护共享钱包，但“真实扣款总有一笔发现余额不足”缺少实现依据。订单锁仍负责每笔订单自身的幂等，只是不能代替钱包锁。当前 updateBalance 是将 Java 计算出的余额直接写回，不会自动再次检查余额；若两个事务都普通读取 100，再分别写回 20，可能两笔订单都成功、主播合计入账 160，而观众余额只减少 80，形成丢失更新与账务不平。UPDATE 自带的写锁不能修复此前在锁外读取并计算的旧值。项目实际通过钱包 SELECT ... FOR UPDATE，在读取余额之前串行化共享钱包访问。

**参考答案（可口述）：**

订单锁只能防止同一订单重复执行，不同订单共用钱包还需要钱包级并发控制。不能默认数据库会自动判断余额不足：如果两笔订单都读到 100，各自算出 20 再写回，可能两笔都成功，但观众只少了 80，主播却合计增加了 160。

项目在同一个账务事务中，用 SELECT balance FROM wallet_account WHERE user_id = ? FOR UPDATE 锁定钱包并读取余额，再检查是否足够。两个事务争用同一个观众钱包时，后一个必须等待；先执行的扣掉 80 并提交后，后一个通过锁定读拿到的是 20，于是将自己的订单标记为余额不足失败，不再扣款或入账。若第一个事务回滚，等待者可基于回滚后的余额继续判断。

观众和主播的钱包都要保护，避免并发扣款或并发入账的更新丢失；双方钱包、双方流水和订单变更在同一事务中完成。项目按用户 ID 从小到大锁定钱包，以降低交叉送礼的死锁风险。

**代码依据：** GiftService.processOrder 的 firstUserId/secondUserId、balanceForUpdate、余额检查和 markFailed；WalletRepository.balanceForUpdate/updateBalance。本轮未运行测试。

## Q005：双方钱包的加锁顺序与死锁

**面试官问题：** A 给 B 送礼，B 同时给 A 送礼。如果两边都先锁付款人钱包、再锁收款人钱包，会发生什么？你会怎样规定加锁顺序？如果仍然发生数据库死锁，消费者应该怎样处理？

**用户回答：** 最初回答“不知道诶”，随后补充：会发生死锁。A 向 B 送礼先锁 A 钱包，但要访问的 B 钱包已经因为 B 向 A 送礼被锁住，双方互相等待；具体加锁顺序不清楚。

**评价与改进：** 已理解相反加锁顺序可能形成循环等待。修正：锁收款人钱包主要为了读取并安全更新其入账余额，不是检查收款人是否余额充足。需要掌握按稳定的 userId 顺序申请双方钱包锁，而不是按付款人、收款人这种随交易改变的角色排序。固定钱包锁顺序用于降低该类死锁风险，不能保证其他事务路径也绝无死锁。

**参考答案（可口述）：**

如果每笔交易都先锁付款人再锁收款人，就可能死锁：事务 T1 处理 A 给 B 送礼，持有 A 的钱包锁并等待 B；事务 T2 处理 B 给 A 送礼，持有 B 的钱包锁并等待 A，形成循环等待。

解决方法是所有交易都按用户 ID 从小到大锁钱包，不随付款方向变化。假设 A 的 ID 为 1，B 为 2，无论 A 给 B 还是 B 给 A，都先锁 A，再锁 B。两个事务竞争同一把 A 锁，一个先获得，另一个在还没占住 B 时等待；先获得 A 的事务可以继续获得 B，执行完提交，再由另一个执行，从而避免这条相反顺序导致的循环等待。锁的获取顺序与扣款、入账的业务方向是两回事，先锁 A 并不代表 A 一定付款。

项目代码先计算 Math.min(senderId, anchorId) 和 Math.max(senderId, anchorId)，然后依次调用 balanceForUpdate。锁持有到事务提交或回滚。如果其他路径仍触发数据库死锁，被选为牺牲者的事务回滚并将异常传播给消费者；监听器返回 RECONSUME_LATER，由 RocketMQ 后续重试整个事务，订单幂等保护重复处理。

**代码依据：** GiftService.processOrder 的钱包 ID 排序及 @Transactional；WalletRepository.balanceForUpdate；GiftOrderMessageListener 的异常重试分支。本轮未运行测试。

## Q006：固定加锁顺序理解检查

**面试官问题：** A 的 userId 为 10，B 的 userId 为 20。现在 B 给 A 送礼，按照项目规则先锁谁的钱包？为什么不能因为 B 是付款人就先锁 B？

**用户回答：** 原因是A的钱包,因为因为我们不是按照收款人和付款人这个顺序来所钱包的，而是按照用户ID的大小，从小到大来锁定钱包的。

**评价与改进：** 回答正确，已理解本题：先锁 A（10），再锁 B（20），固定钱包加锁顺序不受付款方向影响。无需额外纠正。口述中的重复和转写不影响技术判断。

**答案确认：** 先锁 A，因为 10 小于 20。所有涉及这两个钱包的交易都按同一顺序获取锁，避免双方各持有一把钱包锁后互相等待。

## Q007：账务提交后、消费确认前宕机

**面试官问题：** 消费者已经提交了观众扣款、主播入账和订单 SUCCESS 状态，但还没向 RocketMQ 返回消费成功就宕机。消息再次投递时，会不会重复扣款？请按事务与订单状态说明处理过程。

**用户回答：** 不会重复扣款了，因为订单已经，订单状态已经变成 successful。

**评价与改进：** 结论正确，但需补上执行过程及事务前提。项目实际状态值是 SUCCESS。消息重投后仍需执行订单锁定读，发现非 PENDING 后跳过资金与流水变更，并正常返回消费成功。不会重复扣款的依据是资金、流水、订单终态同事务提交，以及重试时的状态门禁，而不只是抽象地说状态已经改变。

**参考答案（可口述）：**

不会重复扣款。前一个消费者已经在同一个事务中提交了观众扣款、主播入账、双方流水和订单 SUCCESS 状态，因此账务结果与订单状态是一致的。

**面试官问题：** 实例 2 与 Redis 的订阅连接断开了 5 秒，这期间实例 1 发布了 10 条已落库弹幕。订阅恢复后，Redis 会自动补发这 10 条吗？B 的 WebSocket 如果一直没断，项目会自动帮他补齐吗？请区分实时订阅恢复和客户端重连补历史。

## Q011：弹幕广播为什么选择 Pub/Sub

**面试官问题：** 既然 Redis Pub/Sub 可能丢实时消息，而项目已经有 RocketMQ，为什么弹幕广播仍使用 Pub/Sub？如果改成多个 Live 实例在同一个消费者组里消费 RocketMQ，能直接保证同一直播间所有实例的观众都收到吗？

**用户回答：** 不使用 RocketMQ主要有两方面的考虑，一方面是当消费者消费完一条消息之后，这条消息就永久地标记为已处理了，所以不可能让所有节点都收到这条弹幕。然后另一个方面是，如果要用 RocketMQ的话，一步处理时间会很长，而弹幕比较强调时效性，所以说就选用 Redis Pub/Sub。

**评价与改进：** 已抓住广播和实时性两个方向，但消费模型解释不准确，延迟结论也缺少压测依据。RocketMQ 在同组集群消费下分摊处理消息，不能直接实现每实例接收全部事件；这是消费模型的选择，不是消费确认后全局永久删除消息。不同消费者组有独立消费进度；传统客户端还支持广播消费，具体可用能力应核对客户端版本。不能泛化为 RocketMQ 无法广播或延迟一定很长。选择 Pub/Sub 的合理表达是实时扇出简单、无需额外维护这条链路的持久消费进度，接受实时通知可能丢失的边界；历史查询虽由 MySQL 承担，但当前自动补偿并不完整。

**参考答案（可口述）：**

弹幕要求把同一个房间事件送到所有持有该房间连接的 Live 实例，再由各实例广播给本地观众。Redis Pub/Sub 直接支持在线订阅者的实时扇出，接入简单；历史弹幕已经落在 MySQL，因此当前把实时广播与历史查询分开。但 Pub/Sub 会丢失订阅断连期间的事件，现有补偿也有缺口，这个边界必须承认。

如果把所有 Live 实例放在 RocketMQ 同一消费者组并采用集群消费，一条消息通常只由组内一个实例处理，其他实例不会都拿到，不能直接满足跨节点广播。这并不表示 RocketMQ 不能广播：可以根据客户端能力采用广播消费，或设计独立消费者组等方案，但要额外考虑实例生命周期、订阅和消费进度管理。

所以选 Pub/Sub 是当前实时扇出需求、实现复杂度与可靠性边界之间的取舍，不是因为 RocketMQ 天生很慢。我没有给出两者的对照压测，不能断言 RocketMQ 一定达不到弹幕延迟要求。

**原理参考：** [Apache RocketMQ 消费模型说明（release-4.9.2）](https://apache.googlesource.com/rocketmq/+/refs/heads/release-4.9.2/docs/en/Concept.md)、[Apache RocketMQ 消费者运维说明](https://github.com/apache/rocketmq/blob/develop/docs/en/Operations_Consumer.md)。分别说明集群/广播模型和不同组独立消费进度；传统版本能力不自动代表所有 5.x 客户端能力。

## Q012：多连接下的在线人数统计

**面试官问题：** 同一个用户开两个标签页进入同一直播间，两个连接还可能落在不同 Live 实例。在线人数应该算几个人？如果关闭其中一个标签页，直接从房间在线用户集合里删掉 userId 会有什么问题？你项目怎么处理？

**用户回答：** 同一个用户同时开两个标签进入一个直播间，在线人数应该算一个人。然后关闭其中一个标签的时候，先会校验当前这个用户开了几个直播间。如果关掉这个标签就变为零的话，会直接删除这个 user ID，否则的话只是在原来的数字上减一。

**评价与改进：** 业务语义正确：同房间按用户去重，只在最后一个有效连接消失时移除在线用户。需将“开了几个直播间”改为“该用户在这个房间还有几条有效连接”。实际实现不是一个简单计数器加减，而是两层 Redis ZSet：房间用户集合与用户在该房间的连接集合。离开时移除具体连接并清理超时连接，再判断是否为空；Lua 保证该多步更新原子执行，避免并发心跳与关闭交错造成错误。连接标识应跨节点、跨进程启动区分，且需处理未触发关闭回调的故障。

**参考答案（可口述）：**

在线人数按同一个房间内的 userId 去重，所以两个标签页算一个人。关闭一条连接时不能直接移除 userId，因为这个用户可能还有另一条连接在线。

项目用两层 Redis ZSet：房间级 ZSet 的 member 是 userId，用来统计去重人数；用户在房间中的连接级 ZSet 的 member 是带节点和进程启动标识的 connectionId，score 是心跳时间。心跳更新连接和用户的活跃时间。

关闭标签页时，通过 Lua 原子移除当前连接、清理该用户的过期连接，再检查连接 ZSet 是否为空。只有没有其他有效连接时，才从房间 ZSet 移除 userId；否则保留用户在线状态。这样不是盲目对计数器减一，重复关闭同一连接也不会重复扣减计数。异常断线则还需要依靠心跳超时回收，不能只依赖关闭回调。

**代码依据：** OnlinePresenceService 的 HEARTBEAT_SCRIPT、LEAVE_SCRIPT、onlineCount 和 presenceId；此前项目资料中的节点启动标识说明。本轮未运行测试。

**评价与改进：** 理解了“停止刷新心跳后超时失效”，但还需明确数据结构、清理主体和 TTL 边界。浏览器可能仍尝试发送或正在重连，关键是宕机实例不能再为这些连接更新 Redis 心跳分数。房间 ZSet 中每个 userId 有独立的最后活跃时间 score；ZSet member 不因 score 过期自动删除，需程序执行按分数清理。只设置整个 Key 的 TTL 无法在房间持续活跃时逐个淘汰失联用户；同用户其他连接仍活跃时，应保留该用户。

## Q015：秒杀链路与库存预扣

**面试官问题：** 介绍一下限时秒杀从收到请求到订单成功的完整过程。Redis、MySQL 和 RocketMQ 各自负责什么？特别说明先在哪一层检查并预扣库存，以及 MySQL 是在发 MQ 前还是消费 MQ 时创建订单。请按当前项目实际实现回答。

**评价与改进：** 主顺序正确，明确了订单在发送 MQ 前就已写入 MySQL，避免套用“只过 Redis，消费者首次建单”的常见模板。需具体说明“用户状态”是该活动的用户参与占位，而不是账号登录状态；Lua 同时完成重复参与检查、库存检查、库存减一和登记参与用户。还应补充入口先查 MySQL 的活动状态、时间与已有订单，以及 CREATE/CLOSE 两类 Outbox 和最终状态推进。MQ 缓冲的是后续处理，不能消除入口查询与建单的数据库压力。当前活动订单未接入真实支付或钱包扣款。

**参考答案（可口述）：**

活动启动时先将库存预热到 Redis。秒杀请求进入后，先从 MySQL 校验活动状态、起止时间并检查用户已有订单；已有订单按其状态返回或触发待处理消息补偿。

没有已有订单时，执行 Redis Lua：检查用户是否已参与、库存是否大于零，通过后原子扣减库存并将 userId 加入活动参与集合，完成库存预占和一人一单控制。预占成功后，在同一个 MySQL 本地事务里创建 PENDING 订单，以及 CREATE 和延迟 CLOSE 两类 Outbox 事件，接口返回当前订单状态。

Redis 负责原子预占，MySQL 保存活动与订单事实，MQ 异步化后续处理并缓冲积压。由于入口仍然查库、写订单，不能说 MQ 屏蔽了所有入口数据库压力；当前 CREATE 不执行真实支付或钱包扣款。
