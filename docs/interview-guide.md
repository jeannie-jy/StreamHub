# StreamHub 面试讲解提纲

## 一分钟介绍

StreamHub 是一个面向高并发场景的直播互动与虚拟礼物平台。SRS 负责音视频推拉流，Spring Boot 服务负责直播间、用户、礼物、钱包和活动，Realtime Gateway 负责 WebSocket 长连接。Redis 承载在线状态、榜单、库存和限流，RocketMQ 负责礼物和秒杀订单异步处理，MySQL 保存最终业务事实。

## 三个核心亮点

### 多节点弹幕

WebSocket 连接绑定在单个 Live 节点的内存注册表中。客户端发来的弹幕先落 MySQL，再发布包含 eventId 和 sourceNodeId 的 RoomEvent 到 Redis Pub/Sub；每个节点只向自己的连接广播。这样扩容只增加连接承载能力，跨节点消息仍能到达。断线消息通过 MySQL 的 afterId 接口补偿。

### 礼物幂等

礼物请求用客户端订单号建立唯一边界，订单先进入 PENDING，再由 RocketMQ 异步处理。扣款流水使用唯一业务号，消费者重复执行时直接返回已有流水结果。余额、流水和订单在 MySQL 内形成可追溯事实，Redis 榜单和 WebSocket 动画都是成功订单的派生结果。

### 秒杀削峰

入口只做轻量鉴权和 Redis Lua 原子预扣，成功请求写入 RocketMQ 后立即返回 PENDING。消费者再创建 MySQL 订单，唯一索引处理重复消息；延迟消息关闭超时订单并回补库存。Redis、MQ 和 MySQL 不一致时，以订单状态对账并执行补偿。

## 面试边界

- “百万级”指 CDN 和媒体服务器承载观看分发，需同时说明互动连接数、业务请求量、节点数量和压测条件。
- Redis Pub/Sub 只适合在线实时广播，不能代替可靠消息存储。
- RocketMQ 解决异步削峰和重试，但不能自动保证跨 Redis/MySQL 的分布式事务。
- 先保证库存、钱包和订单正确，再根据指标决定是否做分库分表、房间分片或批量合并。

## 常见追问

| 追问 | 回答要点 |
| --- | --- |
| 为什么 WebSocket 不直接连 Live 服务？ | 独立网关便于连接层单独扩容、鉴权和限流，业务节点只处理房间事件。 |
| Redis 挂了会怎样？ | 在线状态和实时广播受影响；弹幕已先写 MySQL，客户端可补偿。活动预扣会失败并返回错误，恢复后重试。 |
| MQ 重复投递怎么办？ | 订单号、钱包流水业务号和 MySQL 唯一索引共同提供幂等边界。 |
| 如何证明没有超卖？ | 压测后核对 Redis 剩余库存、MySQL 订单数量和成功订单用户集合，库存不能为负且每用户最多一笔。 |
| 如何定位慢请求？ | 用响应 traceId 关联网关和服务日志，结合 Prometheus HTTP p95、JVM、连接池和数据库慢 SQL。 |
